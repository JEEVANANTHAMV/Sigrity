# Workarounds: Manual Reroute in Dense Area Produces New Spacing Violations

## Verified Workaround

Two practical approaches, depending on the region:

**For sparse/medium-density areas** (where a clean path exists and is discoverable): use the **iterate-and-recheck** loop, which is fast and genuinely practical:
```
start_allegro_session()
allegro_assign_net(session_id, "PIN", "<a pin on the bad net>", "<that net's own name>", ripup=True)
allegro_create_trace(session_id, points=[...surveayed path...], layer="TOP", net_name="<net>", width=5.0)
allegro_save_design(session_id)
allegro_run_session(session_id, board_file=...)
wait_for_job(...)
run_allegro_batch_drc(board_file=...) ; wait_for_job(..., timeout_seconds=15)   # read batch_drc.log
run_allegro_report(..., report_code="drc")   # read new violations; adjust if needed
run_allegro_report(..., report_code="sum")   # confirm Nets/Pins/Connection Completion unchanged
```
Each full DRC+report re-check cycle takes under 2 seconds; each Allegro session run takes ~5-6s. Survey the local neighborhood with repeated `axlDBGetConnect` queries (live, in-session) before choosing the final path points. In the measured case (net X8, 8-line parallel mux bus through a dense analog pocket), even a maximally-surgical reroute left double-digit new spacing violations after multiple iterations.

**For dense areas** (where a fully clean path is unlikely to be discoverable by hand): **prefer the SPECCTRA autorouter**. Export the board to `.dsn` via `run_spif_export_to_specctra`, route via `run_specctra_autoroute`, and import the result via `run_allegro_specctra_import` (the confirmed-live import path, NOT the crash-prone `run_specctra_import_session`). The autorouter has global keepout/spacing awareness that a manual point-coordinate workflow does not.

Evidence: `.forjinn/skills/sigrity-cad/SKILL.md:488-491` — "The mechanical loop itself (rip-up → create → save → run → batch_drc → report) is fast ... and genuinely practical for iterate-and-recheck — but it does not replace an autorouter's or a human's keepout awareness for a dense board region."

## Prevention

1. Before a manual rip-up-and-refix, **survey the local neighborhood** with `axlDBGetConnect` queries (live, in the same SKILL session). Identify all nearby copper objects within the routing corridor. This is the tool chain's equivalent of "read the keepout map before routing."
2. In dense areas (8+ parallel buses, multiple nets sharing a small region), **prefer the SPECCTRA autorouter** over manual point-coordinate rerouting. The tool chain is not the bottleneck; geometric complexity is.
3. Use the iterate-and-recheck loop (fast, under 2s per DRC+report cycle) to converge on a clean path in sparse/medium areas. Do not expect a single-shot success in dense areas.
4. After each iteration, read `run_allegro_report(report_code="drc")` for the FULL list of new violations (not just the targeted one). Adjust the path points and repeat. Verify with `run_allegro_report(report_code="sum")` that Nets/Pins/Connection Completion are unchanged (no collateral damage).

## Remaining Gaps

- **No in-suite "keepout map" query**: there is no tool that returns "all copper objects within X mils of this polyline" in a single call. Neighbors must be discovered one at a time via `axlDBGetConnect` on adjacent named objects (nets, components, pins). A dense area with many anonymous trace segments (not tied to named nets on adjacent layers) is particularly hard to survey.
- **No automated meander/detour generator**: the path geometry must be hand-designed or generated by external code. The tool chain can measure lengths (`allegro_get_net_length`) and create traces, but it does not generate collision-free detour geometry.
- **The SPECCTRA autorouter's handling of dense areas is not characterized in this suite's test evidence.** The autorouter worked on the Fault-Detector sample (100% completion, 0 unconnections), but the specific X8 dense-pocket case was not tested via SPECCTRA (the manual rip-up-and-refix investigation was the scope). It is the recommended fallback for dense areas, but its dense-area performance is an assumption based on the tool's known global-optimization capability, not a live-measured result in this specific dense region.
- **Multi-branch net rip-up hang** (see `multi-branch-net-ripup-reroute-hang`): the iterate-and-recheck workflow is confirmed reliable only for single-branch (2-pin) nets. A multi-branch net (e.g., 4-pin) rip-up-and-refix via `allegro_assign_net(ripup=True)` + `allegro_create_trace` made `allegro_run_session` hang for minutes (reproduced 2-for-2). For multi-branch nets in dense areas, the SPECCTRA autorouter is the only confirmed-practical path.
