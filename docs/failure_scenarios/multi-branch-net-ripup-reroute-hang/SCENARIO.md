# Multi-Branch Net Rip-Up & Re-Route Hangs `allegro_run_session` for Minutes

**Slug**: `multi-branch-net-ripup-reroute-hang`
**Tool(s) affected**: `allegro_assign_net` + `allegro_create_trace` together (allegro_geometry_tools.py), observed via `allegro_run_session`
**Status category**: `unreliable_intermittent`
**Pipeline stage**: routing (manual rip-up-and-refix / length-matching)

## Symptom

Ripping up **one branch** of a **multi-branch** net (`allegro_assign_net(object_type="PIN", ..., ripup=True)` on a pin belonging to a net with 3+ pins/branches) and recreating **just that branch** with `allegro_create_trace`, then running the session, causes `allegro_run_session` to **hang for minutes** (vs the normal ~5-6s for this same toolchain on a simple 2-pin/single-branch net). Reproduced **2-for-2** on fresh board copies. The already-documented modal-dialog explanation was explicitly ruled out: `DismissWatcher`'s own window enumeration found **zero** dialog windows during the hang — just the normal main Allegro window, still `Responding=True`. **Root cause not isolated.**

## Root Cause

**Not yet root-caused.** The investigation's leading (unconfirmed) candidate: recreating one branch of a net whose **other** branches/pins are still attached at a shared junction may trigger an expensive connectivity/cline-merge recompute that — at this board's local density — exceeds any reasonable response time, effectively hanging the session within the observed window. No mechanism in this suite (or, as far as was investigated, in Allegro's SKILL/`axlDBCreatePath` layer) was found to confirm or rule out this specific hypothesis; it is recorded as a candidate, not a finding.

What **was** firmly established:

- This is a **distinct** failure from the already-documented modal-Qt-dialog hang and from the ~137s-watchdog hang — the modal explanation was explicitly, live-tested, ruled out (zero dialog windows present during the hang, per `DismissWatcher`'s own enumeration).
- The **same** toolchain (`allegro_assign_net(ripup=True)` + `allegro_create_trace`) is **confirmed reliable (~5-6s, every time)** for a simple **2-pin/single-branch** net — demonstrated twice in the same investigation body (the original single-branch DRC short fix, and the successful length-matching demonstration after switching to a single-branch net pair). The hang is therefore **content/branch-count specific**, not a general failure of the rip-up+refix mechanic.

## Pipeline Impact

Any manual rip-up-and-refix pipeline step (or hand-driven session) that targets a **multi-branch** net — ripped up via `allegro_assign_net(ripup=True)` and recreated via `allegro_create_trace` — is **unreliable on this installation** and can hang `allegro_run_session` indefinitely (observed: minutes, not the normal ~5-6s) with **no dialog to dismiss** (so `DismissWatcher` will not resolve it) and **no root cause** to target. Because there is no in-suite signal that pre-flags "this net is multi-branch and therefore risky" and no confirmed auto-detection/timeout-and-recover mechanism for this specific hang (distinct from the ~137s-watchdog, which at least terminates with a known rc), a pipeline that naively applies this mechanic to an arbitrary net can stall a multi-minute observation window or longer with no automatic recovery path, and — as with any suspiciously long `allegro_run_session` — a downstream `report.exe` call made while the session is still mid-save can silently read **stale, pre-change** board state (see sibling scenario `report-stale-board-mid-save`). There is **no** in-suite code change for this in the current repo (consistent with status `unreliable_intermittent`, `verified_workaround: NO` per the SCENARIOS.md manifest index, row #23).
